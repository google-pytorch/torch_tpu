# TorchTPU 执行模型 { #torchtpu-execution-model }

使用 TorchTPU 执行 PyTorch 程序时，底层会进行许多操作来优化执行。了解这一模型可以帮助您了解如何调优使用体验，并充分利用 TorchTPU 的一些独特优势。

## 执行流水线 { #execution-pipeline }

### 创建延迟算子 { #create-deferred-op }

在 TorchTPU 后端上执行 PyTorch 操作（简称“算子”，即 op）时，TPU 本身最初不会执行任何工作。

相反，计算的逻辑结果会被打包成一个延迟算子（deferred op）。这是一个 CPU 端的内存对象，其中包含执行该操作所需的全部信息，包括其输入、要执行的逻辑步骤，以及输出的形状和类型等。

流水线的其余部分会用真实数据替换这个符号化的延迟算子，这一过程称为具体化（materialization）。

### 将算子加入 stream 队列 { #enqueue-op-on-a-stream }

TorchTPU 支持 `torch.Stream` 接口。每当创建一个 DeferredOp 时，它都会被推送到当前活动的 Stream 中排队，等待之后执行。

此时，调用线程的工作已经完成；之后的所有操作都在后台异步进行（launch-blocking 模式除外，稍后会详细介绍）。

### 分析 stream 并准备执行计划 { #analyze-stream-and-prepare-execution-plan }

当某个 stream 上有待处理的工作时，后台线程会在某个时间点从该 stream 中取出工作。然后，该后台线程会对 stream 上的工作进行整体分析，考虑多种不同的因素，包括：

*   需要将其拆分成多少次单独的执行？
*   每个执行块的输入和输出是什么？
*   每个执行块应采用什么级别的编译优化？
*   之前是否见过每个计算单元，还是它是新的？
*   这项工作应在哪种核心（TensorCore 或 SparseCore）上执行？

通过对待处理的工作进行整体考虑，后台线程可以做出更好的执行决策。

后台线程确定每个块的最终输出后，会将这些输出标记为待处理（pending），表示它们将在未来执行，然后进入下一步。

### 编译（或获取）可执行文件 { #compile-or-fetch-executables }

对于每个执行阶段，后台线程都会检查编译缓存，看看是否已经使用正确的设置编译过可执行文件。默认情况下，这是一个本地内存缓存（第 1 层），您还可以选择启用持久性的设备本地缓存（第 2 层）或远程缓存（第 3 层），以最大限度地降低重新编译的开销。

如果缓存未命中，该单元的编译图会被转换为 MLIR（主要是 StableHLO，用户定义的自定义 kernel 除外），并交给编译线程池。该线程池会异步并行编译多个编译单元，并在编译完成后将其返回给后台工作线程。

### 开始执行 { #start-execution }

收集好输入并准备好可执行文件后，执行任务会被加入 XLA 运行时 [PjRt](https://openxla.org/xla/pjrt) 的队列中。

PjRt 会为这个未来的输出返回 promise，这些 promise 随后会被接入输出，表示它们正在具体化。

### （可选）等待完成 { #optional-wait-for-completion }

如需了解工作何时完成，您可以在 stream 上记录一个 `torch.Event`，然后使用 `torch.Event.query` 方法检查它。

您也可以改用（或同时使用）任意“同步”指令（`torch.Event.synchronize`、`torch.Stream.synchronize`，或用于整个设备的 `torch.accelerator.synchronize`）在 stream 上阻塞，这会暂停您的 Python 代码，直到 TPU 发出完成信号。

## 执行模式 { #execution-modes }

TorchTPU 的编程流水线非常灵活，支持多种不同的执行方式。

### Strict eager 模式 { #strict-eager-mode }

此模式也称为“默认 eager”或“从不延迟”（defer never），提供的是大家熟悉的开箱即用 PyTorch 体验。在此模式下，每个追加到队列的算子都会立即将该 stream 标记为待执行。因此，具体化后台工作线程会逐个处理算子。

这些单算子执行图的优化空间极小，因此会使用较低的 `-O1` 编译级别进行编译，以尽可能提高编译速度。由于存在大量单独的编译，这些编译可以在编译线程池中非常高效地并行进行，而且单个操作的复用程度非常高。因此，在“预热”编译缓存期间，编译开销极小。

请注意，虽然此模式会立即且连续地执行，但执行仍然是异步的；如果您想查看结果，仍然需要进行同步以等待 TPU 完成，而且任何运行时错误都可能在产生它的算子之后很久才显现出来。

### Debug eager 模式 { #debug-eager-mode }

此模式也称为“launch blocking”，可通过设置环境变量 `TORCH_TPU_LAUNCH_BLOCKING=1` 启用。此模式仅用于交互式调试，不适合在生产环境中使用。

此模式与 strict eager 模式（逐个算子执行）相同，不同之处在于主机会在每个操作上阻塞并同步。这会人为地减慢执行速度，但可以确保在发生故障时立即报告，从而帮助您准确定位错误。

### `torch.compile` { #torchcompile }

为了获得最佳性能，`torch.compile` 既能提供更大的优化空间，又能降低运行时开销。

使用 `torch.compile` 编译特定函数或模块时，TorchTPU 后端会以 [FX 图](https://docs.pytorch.org/docs/stable/fx.html)的形式获得编译目标的完整范围。这样可以获得关于预期执行的最多信息，并保证它不会改变，从而使我们能够进行在 eager 模式下风险过高的激进优化。

作为编译模式后端，TorchTPU 会执行一次初始跟踪（使用“占位符”张量，类似于 FakeTensor，但保留了 TPU 特有的元数据），生成一个复刻 FX 图的完全延迟计算图。创建完成后，我们会将这个 StableHLO 程序交给 XLA，使用较高的 `-O2` 优化级别进行编译。然后，该程序会被打包成一个 Python 可调用对象并返回给用户，供之后执行。

调用此可调用对象时，我们会立即跳过大部分 eager 执行步骤。不会创建新的 DeferredOp；不需要进一步的图分析；而且可执行文件已经提供，因此不需要缓存。相反，可执行文件会立即被推送到 PjRt 执行，在使用经 XLA 编译器充分优化的计算图的同时，将主机端开销降到最低。

### Optimized eager 模式 { #optimized-eager-mode }

此模式也称为“Defer and Fuse”模式，可通过设置 `TORCH_TPU_DEFER_AND_FUSE=1` 启用。这是一种新的混合模式，将 `torch.compile` 的许多优势带入了 eager 模式。

在此模式下，创建新的 DeferredOp 不会立即开始执行；我们允许算子在 Python 调用之间保持延迟状态，在 Stream 队列中等待。

满足以下两个条件之一时，我们会开始具体化：

*   用户执行了某些强制执行的操作。其中最常见的是启动设备到主机的传输或显式调用同步。
*   我们检测到分派的算子中出现了重复，这表明我们处于一个循环中，应该编译该循环的一次迭代以便复用。

这会触发后台具体化，与默认 eager 模式类似，区别在于正在编译的图大于单个操作。在发出具体化信号时，任何已被丢弃或覆盖的张量都会被跳过，通常会被融合到下游操作中；如果输出在未被读取的情况下就被丢弃，则会被完全消除。（注意：对于分布式集合通信算子，会跳过死代码消除，以避免跨 TPU 死锁。）

由于这会产生更大的编译图，我们使用优化级别 2（`-O2`）来缩短执行时间。由于我们编译的是数量较少但规模较大的图，编译线程池带来的并行化收益会降低，因此编译时间预计会比 strict eager 模式更长。

虽然 optimized eager 模式的优化程度不如 `torch.compile` 模式，但与默认 eager 模式相比，它无需修改模型代码，即可带来最高 50% 的性能提升。

## 常见陷阱 { #pitfalls }

虽然此执行流水线同时针对延迟和吞吐量进行了优化，但在某些情况下性能仍可能受到影响。

### 所有模式：Python 端控制流和数据相关的形状 { #all-modes-python-side-control-flow-and-data-dependent-shapes }

在 PyTorch 中，很容易在无意中悄无声息地强制进行设备到主机的传输。像“`if my_tensor.all()`”这样的操作会悄悄构造一个布尔值张量，同步 stream，并将该布尔值复制到 CPU，然后才继续执行控制流。

在默认 eager 模式下，这不会强制产生新的图中断，但会强制 stream 的整个执行流水线排空后才能继续。更糟的是，在 optimized eager 模式或编译模式下，这个强制同步点会在 eager 融合的 stream 或 FX 图中强制产生图中断，形成优化屏障。

对于输出形状取决于数据的 PyTorch 操作（例如 `torch.masked_select`），也可能出现类似的行为。由于在计算掩码输入之前无法得知输出张量的大小，这同样会强制进行完全阻塞的 stream 同步，并在继续之前将形状元数据从设备传输到主机。

### Strict eager 模式：过小的可执行文件会导致微气泡 { #strict-eager-mode-tiny-executables-cause-microbubbles }

使用 PjRt 将可执行文件加入队列需要少量时间，通常为 50 微秒或更短。在大多数情况下，每个可执行文件的运行时间都会长于这个时间（即使只有 1 或 2 毫秒），从而完全掩盖这一延迟，使 TPU 进入以峰值效率持续运行的稳定状态。

但是，如果加入队列的可执行文件中有太多低于此阈值（例如在张量较小的情况下使用 strict eager 模式），就可能导致 TPU 饥饿。当 TPU 的运行速度快于 CPU 将更多工作加入队列的速度时，TPU 执行会因受限于分派速度而被细小但频繁的“微气泡”打断。

为避免这种情况，请确保您的模型在每个操作上执行足够多的工作，以抵消这一小的启动开销；或者使用 optimized eager 模式，自动将执行即时融合为编译块。

### 编译模式：将视图作为参数或输出 { #compiled-mode-views-as-arguments-or-outputs }

调用已编译的可执行文件时，PjRt 要求输入值是连续的、偏移量为零的，并且具有特定的数据类型。如果某个张量参数是一个非平凡视图，或者已从原始数据类型进行了位转换（bitcast），TorchTPU 就会在 eager 模式（strict 或 optimized）下为该张量创建一个临时副本，以便正确调用已编译的可执行文件。

为避免创建这种临时副本，请确保已编译函数的所有输入都是连续的。如果您计划按顺序调用多个已编译函数，请确保前面函数的输出是连续的，以免在这些经过优化的函数之间产生 eager 模式的额外开销。

### Optimized eager 模式：保留冗余张量 { #optimized-eager-mode-retaining-redundant-tensors }

在所有 eager 模式下，操作都会按其创建顺序执行，并且每当发出具体化信号时，该时间点所有仍然存活的张量都会被具体化。

如果这些张量中有不重要的中间张量，可能会导致 defer-and-fuse 机制错误地将它们识别为必要的输出并对其进行具体化，从而可能降低编译图的效率。

为了改进融合效果并最大限度地减少内存用量，请务必在不再需要张量时立即清理它们，或者使用原地操作将过时的张量替换为当前值。

## 要点总结 { #takeaways }

TorchTPU 的延迟执行模型可在多种编译时间/运行时间权衡下提供高效的流水线处理。

*   **如需最短的编译时间**：使用 strict eager 模式（默认模式）。此模式会立即开始执行并并行编译，以尽可能缩短获得第一个结果的时间。
*   **如需在预热后获得最大吞吐量和最低延迟**：使用 `torch.compile`。这几乎消除了 eager 模式的所有开销，并最大限度地发挥编译器的优化潜力。
*   **如果更看重运行速度，但无法使用 `torch.compile`**：可以考虑使用 optimized eager 模式。
*   **如需调试**：使用 launch-blocking 模式，强制 CPU 和 TPU 步调一致地运行。
*   **避免强制同步**：保留最少的一组连续张量，并使用计算密集型操作，让 TPU 始终有充足的有效工作可做。
