# TorchTPU の実行モデル { #torchtpu-execution-model }

TorchTPU を使用して PyTorch プログラムを実行すると、実行を最適化するために内部でさまざまな処理が行われます。このモデルを理解すると、エクスペリエンスをチューニングする方法を把握し、TorchTPU 独自の強みを活用するのに役立ちます。

## 実行パイプライン { #execution-pipeline }

### 遅延演算を作成する { #create-deferred-op }

PyTorch の演算（または単に「op」）が TorchTPU バックエンドで実行されると、最初は TPU 自体では何も処理が行われません。

代わりに、計算の論理的な結果が遅延演算（deferred op）にパッケージ化されます。これは CPU 側のメモリ オブジェクトで、この演算を実行するために必要なすべての情報（入力、実行する論理的なステップ、出力のシェイプと型など）が含まれています。

このシンボリックな遅延演算を実際のデータに置き換える、パイプラインの残りの部分を実体化（materialization）と呼びます。

### 演算をストリームのキューに追加する { #enqueue-op-on-a-stream }

TorchTPU は `torch.Stream` インターフェースをサポートしています。DeferredOp が作成されるたびに、後で実行するために、その DeferredOp が現在アクティブなストリームにプッシュされてキューに追加されます。

この時点で、呼び出し元のスレッドの処理は完了です。これ以降の処理はすべてバックグラウンドで非同期に行われます（launch-blocking モードを除きます。詳しくは後述します）。

### ストリームを分析して実行計画を準備する { #analyze-stream-and-prepare-execution-plan }

ストリームに処理すべき作業があると、いずれかの時点でバックグラウンド スレッドがそのストリームから作業を取得します。次に、このバックグラウンド スレッドは、次のようなさまざまな要素を考慮して、ストリーム上の作業をまとめて分析します。

*   作業をいくつの個別の実行に分割する必要があるか。
*   各実行ブロックの入力と出力は何か。
*   それぞれにどのレベルのコンパイル最適化を適用するか。
*   各計算ユニットは以前に見たことがあるものか、それとも新しいものか。
*   この作業をどのコア（TensorCore または SparseCore）で実行するか。

処理すべき作業をまとめて考慮することで、バックグラウンド スレッドはより適切な実行の判断を下せます。

バックグラウンド スレッドは、各ブロックの最終的な出力を特定すると、それらの出力が将来実行されることを示すために保留中としてマークし、次のステップに進みます。

### 実行可能プログラムをコンパイル（または取得）する { #compile-or-fetch-executables }

バックグラウンド スレッドは、実行ステージごとにコンパイル キャッシュを確認し、正しい設定で実行可能プログラムがすでにコンパイルされているかどうかを調べます。デフォルトではローカルメモリのキャッシュ（Tier 1）が使用されます。再コンパイルのコストを最小限に抑えるために、デバイスローカルの永続キャッシュ（Tier 2）やリモート キャッシュ（Tier 3）を有効にするオプションもあります。

キャッシュミスの場合、ユニットのコンパイル グラフは MLIR（ユーザー定義のカスタム カーネルを除き、主に StableHLO）に変換され、コンパイル スレッドプールに渡されます。このスレッドプールは、多数のコンパイル ユニットを非同期で並列にコンパイルし、準備ができたらバックグラウンド ワーカー スレッドに返します。

### 実行を開始する { #start-execution }

入力が収集され、実行可能プログラムの準備ができると、XLA のランタイムである [PjRt](https://openxla.org/xla/pjrt) に実行タスクがキューに追加されます。

PjRt はこの将来の出力に対する promise を返します。この promise が出力に接続され、出力が実体化中であることを示します。

### （省略可）完了を待機する { #optional-wait-for-completion }

作業がいつ完了したかを知るには、ストリームで `torch.Event` を記録し、`torch.Event.query` メソッドを使用して検査します。

その代わりに、またはそれに加えて、任意の「synchronize」命令（`torch.Event.synchronize`、`torch.Stream.synchronize`、またはデバイス全体の場合は `torch.accelerator.synchronize`）を使用してストリームでブロックすることもできます。これにより、TPU が完了を通知するまで Python コードが一時停止します。

## 実行モード { #execution-modes }

TorchTPU のプログラミング パイプラインは柔軟で、さまざまな実行形態をサポートしています。

### Strict eager モード { #strict-eager-mode }

「default eager」や「defer never」とも呼ばれるこのモードは、おなじみの、すぐに使える PyTorch のエクスペリエンスです。このモードでは、キューに追加されたすべての演算が、そのストリームを直ちに実行対象としてフラグ付けします。その結果、演算は実体化のバックグラウンド ワーカーによって 1 つずつ処理されます。

これらの単一演算の実行グラフは最適化の余地が最小限であるため、コンパイル速度を最大化するために、より低い `-O1` のコンパイル レベルでコンパイルされます。個別のコンパイルが多数あるため、コンパイル スレッドプールで非常に効果的に並列化され、単一の演算の再利用率も非常に高くなります。その結果、コンパイル キャッシュの「ウォームアップ」中のコンパイルのオーバーヘッドが最小限に抑えられます。

このモードは eager かつ継続的に実行されますが、実行は依然として非同期です。結果を確認したい場合は、TPU の処理が完了するまで待機するための同期が必要です。また、実行時エラーは、そのエラーを発生させた演算よりもかなり後になってから表面化する可能性があります。

### Debug eager モード { #debug-eager-mode }

「launch blocking」とも呼ばれるこのモードは、環境変数 `TORCH_TPU_LAUNCH_BLOCKING=1` を設定すると有効になります。これはインタラクティブなデバッグのみを目的としたもので、本番環境での使用は想定していません。

このモードは Strict eager（演算ごとの実行）と同じですが、ホストがすべての演算でブロックして同期する点が異なります。これにより実行は意図的に遅くなりますが、エラーの箇所を特定しやすいように、障害が発生するとすぐに報告されます。

### `torch.compile` { #torchcompile }

`torch.compile` は、最大のパフォーマンスを得るために、より大きな最適化の余地と、より少ないランタイムのオーバーヘッドの両方を提供します。

特定の関数やモジュールを `torch.compile` でコンパイルすると、TorchTPU のバックエンドにはコンパイル対象の全体が [FX グラフ](https://docs.pytorch.org/docs/stable/fx.html)として渡されます。これにより、意図された実行に関する最大限の情報と、それが変わらないという保証が得られるため、eager モードではリスクが高すぎる積極的な最適化を行うことができます。

コンパイルモードのバックエンドとして、TorchTPU は最初に 1 回トレースを行い（FakeTensor に似ていますが、TPU 固有のメタデータを保持する「プレースホルダ」テンソルを使用します）、FX グラフを再現する完全に遅延された計算グラフを生成します。これが作成されると、この StableHLO プログラムを XLA に渡し、より高い `-O2` の最適化レベルでコンパイルします。このプログラムは Python の callable にパッケージ化され、後で実行するためにユーザーに返されます。

この callable が呼び出されると、eager 実行のステップのほとんどが直ちにバイパスされます。新しい DeferredOp は作成されず、グラフの追加分析も不要で、実行可能プログラムはすでに提供されているためキャッシュも必要ありません。代わりに、実行可能プログラムは直ちに PjRt にプッシュされて実行されます。これにより、XLA コンパイラによって完全に最適化された計算グラフを使用しながら、ホスト側のコストを最小限に抑えられます。

### 最適化された eager モード { #optimized-eager-mode }

「Defer and Fuse」モードとも呼ばれるこのモードは、`TORCH_TPU_DEFER_AND_FUSE=1` を設定すると有効になります。これは新しいハイブリッド モードで、`torch.compile` の利点の多くを eager モードにもたらします。

このモードでは、新しい DeferredOp を作成しても直ちに実行は開始されません。演算は Python の呼び出し間で遅延されたままになり、ストリームのキューで待機します。

実体化は、次の 2 つの条件のいずれかが満たされたときに開始されます。

*   ユーザーが実行を強制するアクションを行った場合。最も一般的なのは、デバイスからホストへの転送の開始や、明示的な synchronize の呼び出しです。
*   ディスパッチされた演算の繰り返しを検出した場合。これはループ内にいることを示しており、そのループの 1 回の反復をコンパイルして簡単に再利用できるようにする必要があります。

これによりバックグラウンドでの実体化が通知されます。これはデフォルトの eager モードと似ていますが、コンパイルされるグラフが単一の演算よりも大きい点が異なります。実体化のシグナルが発生した時点ですでに破棄または上書きされているテンソルはスキップされます。通常、それらは下流の演算に融合されるか、出力が読み取られずに破棄される場合は完全に除去されます（注: TPU 間のデッドロックを避けるため、分散集団通信演算ではデッドコードの除去はスキップされます）。

これによりコンパイル グラフが大きくなるため、実行時間を改善するために最適化レベル 2（`-O2`）を使用します。より大きなグラフを少数コンパイルすることになるため、コンパイル スレッドプールによる並列化のメリットが小さくなり、コンパイル時間は Strict eager よりも長くなることが予想されます。

最適化された eager モードは、`torch.compile` モードほど最適化されていませんが、モデルのコードを変更することなく、デフォルトの eager に比べて最大 50% のパフォーマンス向上を示します。

## 落とし穴 { #pitfalls }

この実行パイプラインはレイテンシとスループットの両方に対して最適化されていますが、パフォーマンスが低下する場合があります。

### すべてのモード: Python 側の制御フローとデータ依存のシェイプ { #all-modes-python-side-control-flow-and-data-dependent-shapes }

PyTorch では、意図せずに、気づかないうちにデバイスからホストへの転送を強制してしまうことがよくあります。「`if my_tensor.all()`」のような演算は、ブール値のテンソルを暗黙的に構築し、ストリームを同期して、制御フローを続行する前にそのブール値を CPU にコピーします。

デフォルトの eager モードでは、これによって新たなグラフ ブレークは強制されませんが、続行する前にストリームの実行パイプライン全体が空になるまで待つことが強制されます。さらに悪いことに、最適化された eager モードやコンパイルモードでは、この強制的な同期ポイントによって、eager で融合されたストリームまたは FX グラフのいずれかでグラフ ブレークが強制され、最適化の障壁が生じます。

`torch.masked_select` のように、出力シェイプがデータに依存する PyTorch の演算でも同様の動作が発生する可能性があります。出力テンソルのサイズはマスク入力が評価されるまでわからないため、この場合も、続行する前に完全にブロッキングするストリームの同期と、シェイプ メタデータのデバイスからホストへの転送が強制されます。

### Strict eager モード: 小さな実行可能プログラムがマイクロバブルを引き起こす { #strict-eager-mode-tiny-executables-cause-microbubbles }

PjRt で実行可能プログラムをキューに追加するには、通常 50 マイクロ秒以下のわずかな時間がかかります。ほとんどの場合、各実行可能プログラムはこれよりも長い時間がかかり（たとえ 1～2 ミリ秒だけであっても）、このレイテンシを完全に隠すため、TPU がピーク効率で継続的に動作する定常状態になります。

しかし、Strict eager モードで小さなテンソル サイズを使用する場合など、このしきい値を下回る実行可能プログラムが大量にキューに追加されると、TPU のスターベーションにつながる可能性があります。CPU がさらに作業をキューに追加するよりも速く TPU が実行されると、ディスパッチ速度がボトルネックとなり、TPU の実行が小さいながらも頻繁な「マイクロバブル」によって中断されます。

これを避けるには、各演算でこのわずかな起動オーバーヘッドを上回る十分な量の作業をモデルが行うようにするか、最適化された eager モードを使用して実行をその場でコンパイル ブロックに自動的に融合します。

### コンパイルモード: 引数または出力としてのビュー { #compiled-mode-views-as-arguments-or-outputs }

コンパイル済みの実行可能プログラムを呼び出すとき、PjRt では入力値が連続していて、オフセットがゼロで、特定のデータ型である必要があります。テンソルの引数が自明でないビューである場合や、元のデータ型からビットキャストされている場合、TorchTPU はコンパイル済みの実行可能プログラムを正しく呼び出すために、eager モード（Strict または最適化）でテンソルの一時的なコピーを作成します。

この一時的なコピーを防ぐには、コンパイル済みの関数へのすべての入力が連続していることを確認してください。複数のコンパイル済みの関数を連続して呼び出す予定の場合は、最適化された関数の間で eager モードによる摩擦が生じないように、前の関数の出力が連続していることを確認してください。

### 最適化された eager モード: 冗長なテンソルの保持 { #optimized-eager-mode-retaining-redundant-tensors }

すべての eager モードで、演算は作成された順序で実行されます。実体化のシグナルが発生するたびに、その時点で存在しているすべてのテンソルが実体化されます。

これらのテンソルの中に重要でない中間テンソルが含まれていると、defer-and-fuse メカニズムがそれらを必要な出力として誤って識別して実体化し、コンパイル グラフの効率が低下する可能性があります。

融合を改善してメモリ使用量を最小限に抑えるには、不要になったテンソルはすぐにクリーンアップするか、インプレース演算を使用して古いテンソルを現在の値に置き換えてください。

## まとめ { #takeaways }

TorchTPU の遅延実行モデルは、コンパイル時間と実行時間のさまざまなトレードオフにおいて、効率的なパイプライン処理を提供します。

*   **コンパイル時間を最小限にする場合:** Strict eager モード（デフォルト）を使用します。このモードは直ちに実行を開始し、コンパイルを並列化して、最初の結果が得られるまでの時間を最短にします。
*   **ウォームアップ後のスループットを最大にし、レイテンシを最小限にする場合:** `torch.compile` を使用します。これにより、eager モードのオーバーヘッドがほぼすべて排除され、コンパイラの最適化の余地が最大になります。
*   **実行時間を短縮したいものの、`torch.compile` を使用できない場合:** 最適化された eager モードの使用を検討してください。
*   **デバッグする場合:** launch-blocking モードを使用して、CPU と TPU を足並みをそろえて動作させます。
*   **強制的な同期を避ける:** 連続したテンソルの最小限のセットを保持し、計算密度の高い演算を使用して、TPU に生産的な作業を十分に供給し続けます。
