# TorchTPU 실행 모델 { #torchtpu-execution-model }

TorchTPU를 사용하여 PyTorch 프로그램을 실행하면 실행을 최적화하기 위해 내부적으로
많은 일이 일어납니다. 이 모델을 이해하면 사용 환경을 조정하는 방법을 파악하고
TorchTPU의 고유한 강점을 활용하는 데 도움이 됩니다.

## 실행 파이프라인 { #execution-pipeline }

### 지연 연산 생성 { #create-deferred-op }

PyTorch 연산(또는 간단히 "op")이 TorchTPU 백엔드에서 실행될 때 처음에는 TPU
자체에서 아무 작업도 수행되지 않습니다.

대신 계산의 논리적 결과가 지연 연산(deferred op)으로 패키징됩니다. 지연 연산은
이 연산을 수행하는 데 필요한 모든 정보, 즉 입력, 수행할 논리적 단계, 출력의
형상과 타입 등을 담고 있는 CPU 측 메모리 객체입니다.

이 기호적인 지연 연산을 실제 데이터로 대체하는 파이프라인의 나머지 부분을
구체화(materialization)라고 합니다.

### 스트림에 연산 추가 { #enqueue-op-on-a-stream }

TorchTPU는 `torch.Stream` 인터페이스를 지원합니다. DeferredOp가 생성될 때마다
현재 활성 Stream에 푸시되어 나중에 처리되도록 대기열에 추가됩니다.

이 시점에서 호출 스레드의 작업은 끝납니다. 이후의 모든 작업은 백그라운드에서
비동기적으로 이루어집니다(launch-blocking 모드는 예외이며, 뒤에서 자세히
설명합니다).

### 스트림 분석 및 실행 계획 준비 { #analyze-stream-and-prepare-execution-plan }

스트림에 처리할 작업이 생기면 어느 시점에 백그라운드 스레드가 해당 스트림에서
작업을 가져옵니다. 그런 다음 백그라운드 스레드는 다음을 포함한 다양한 요소를
고려하여 스트림의 작업을 함께 분석합니다.

*   이 작업을 몇 개의 개별 실행으로 나누어야 하나요?
*   각 실행 블록의 입력과 출력은 무엇인가요?
*   각 블록에 어느 수준의 컴파일 최적화를 적용해야 하나요?
*   각 계산 단위를 이전에 본 적이 있나요, 아니면 새로운 것인가요?
*   이 작업을 어떤 코어(TensorCore 또는 SparseCore)에서 실행해야 하나요?

처리할 작업을 종합적으로 고려하므로 백그라운드 스레드가 더 나은 실행 결정을 내릴
수 있습니다.

백그라운드 스레드가 각 블록의 최종 출력을 식별하면, 이러한 출력을 대기 중으로
표시하여 나중에 실행될 것임을 나타내고 다음 단계로 진행합니다.

### 실행 파일 컴파일(또는 가져오기) { #compile-or-fetch-executables }

각 실행 단계에서 백그라운드 스레드는 컴파일 캐시를 확인하여 올바른 설정으로
이미 컴파일된 실행 파일이 있는지 확인합니다. 기본적으로 로컬 메모리
캐시(계층 1)를 사용하며, 재컴파일 비용을 최소화하기 위해 영구 디바이스 로컬
캐시(계층 2)나 원격 캐시(계층 3)를 사용 설정하는 옵션이 있습니다.

캐시 부적중 시에는 해당 단위의 컴파일 그래프가 MLIR(사용자 정의 커널을
제외하면 주로 StableHLO)로 변환되어 컴파일 스레드 풀로 전달됩니다. 이 스레드
풀은 여러 컴파일 단위를 비동기적으로 병렬 컴파일하고, 준비되면 백그라운드 워커
스레드에 반환합니다.

### 실행 시작 { #start-execution }

입력이 수집되고 실행 파일이 준비되면 실행 작업이 XLA의 런타임인
[PjRt](https://openxla.org/xla/pjrt)의 대기열에 추가됩니다.

PjRt는 이 향후 출력에 대한 프로미스를 반환하며, 이 프로미스는 출력에 연결되어
출력이 구체화 중임을 나타냅니다.

### (선택사항) 완료 대기 { #optional-wait-for-completion }

작업이 완료되었는지 알려면 스트림에 `torch.Event`를 기록하고
`torch.Event.query` 메서드를 사용하여 확인하세요.

또는 이와 함께 "synchronize" 명령(`torch.Event.synchronize`,
`torch.Stream.synchronize` 또는 전체 디바이스의 경우
`torch.accelerator.synchronize`)을 사용하여 스트림에서 블로킹할 수 있습니다.
이 명령은 TPU가 완료 신호를 보낼 때까지 Python 코드를 일시 중지합니다.

## 실행 모드 { #execution-modes }

TorchTPU의 프로그래밍 파이프라인은 유연하며 여러 가지 실행 방식을 지원합니다.

### Strict eager 모드 { #strict-eager-mode }

"기본 eager" 또는 "defer never"라고도 하는 이 모드는 익숙한 기본 PyTorch
환경입니다. 이 모드에서는 대기열에 추가되는 모든 연산이 즉시 해당 스트림을 실행
대상으로 표시합니다. 그 결과 구체화 백그라운드 워커가 연산을 하나씩
처리합니다.

이러한 단일 연산 실행 그래프는 최적화 여지가 거의 없으므로, 컴파일 속도를
최대화하기 위해 더 낮은 `-O1` 컴파일 수준으로 컴파일됩니다. 개별 컴파일이 많기
때문에 컴파일 스레드 풀에서 매우 효과적으로 병렬화되며, 단일 연산의 재사용
수준이 매우 높습니다. 그 결과 컴파일 캐시를 "워밍업"하는 동안 컴파일 오버헤드가
최소화됩니다.

이 모드는 즉시 연속적으로 실행하지만 여전히 비동기적으로 실행한다는 점에
유의하세요. 결과를 확인하려면 TPU가 완료될 때까지 기다리는 동기화가 여전히
필요하며, 런타임 오류는 오류를 일으킨 연산보다 훨씬 나중에 나타날 수 있습니다.

### Debug eager 모드 { #debug-eager-mode }

"launch blocking"이라고도 하며, 환경 변수 `TORCH_TPU_LAUNCH_BLOCKING=1`을
설정하여 사용 설정합니다. 이 모드는 대화형 디버깅 전용이며 프로덕션용이 아닙니다.

이 모드는 strict eager(연산별 실행)와 같지만, 호스트가 모든 연산에서 블로킹하고
동기화한다는 점이 다릅니다. 이로 인해 실행이 인위적으로 느려지지만, 오류가
발생하는 즉시 보고되므로 오류 위치를 정확히 찾는 데 도움이 됩니다.

### `torch.compile` { #torchcompile }

최고 성능을 위해 `torch.compile`은 더 큰 최적화 여지와 더 낮은 런타임 오버헤드를
모두 제공합니다.

특정 함수나 모듈을 `torch.compile`로 컴파일하면 TorchTPU 백엔드는 컴파일 대상의
전체 범위를 [FX 그래프](https://docs.pytorch.org/docs/stable/fx.html)로 받습니다.
이를 통해 의도된 실행에 관한 정보를 최대한 얻을 수 있고 그 내용이 바뀌지 않는다는
보장도 얻으므로, eager 모드에서는 너무 위험한 적극적인 최적화를 수행할 수
있습니다.

컴파일 모드 백엔드로서 TorchTPU는 초기 트레이스를 한 번 수행하여(FakeTensor와
비슷하지만 TPU 전용 메타데이터를 유지하는 "placeholder" 텐서 사용) FX 그래프를
복제하는 완전히 지연된 계산 그래프를 생성합니다. 이 그래프가 생성되면 StableHLO
프로그램을 XLA에 전달하여 더 높은 `-O2` 최적화 수준으로 컴파일합니다. 그런 다음
이 프로그램을 Python 호출 가능 객체로 패키징하여 나중에 실행할 수 있도록
사용자에게 반환합니다.

이 호출 가능 객체를 호출하면 대부분의 eager 실행 단계를 즉시 건너뜁니다. 새
DeferredOp가 생성되지 않고, 추가 그래프 분석이 필요하지 않으며, 실행 파일이 이미
제공되었으므로 캐싱도 필요하지 않습니다. 대신 실행 파일이 즉시 PjRt로 푸시되어
실행되므로, XLA 컴파일러가 완전히 최적화한 계산 그래프로 호스트 측 비용을
최소화합니다.

### 최적화된 eager 모드 { #optimized-eager-mode }

"Defer and Fuse" 모드라고도 하며, `TORCH_TPU_DEFER_AND_FUSE=1`을 설정하여 사용
설정합니다. 이 모드는 `torch.compile`의 여러 장점을 eager 모드에 도입한 새로운
하이브리드 모드입니다.

이 모드에서는 새 DeferredOp를 생성해도 즉시 실행이 시작되지 않습니다. 연산은
Python 호출 사이에 지연된 상태로 Stream 대기열에서 대기합니다.

다음 두 조건 중 하나가 충족되면 구체화를 시작합니다.

*   사용자가 실행을 강제하는 작업을 수행합니다. 가장 일반적인 경우는
    디바이스-호스트 전송을 시작하거나 명시적인 synchronize 호출을 하는
    것입니다.
*   디스패치된 연산에서 반복이 감지됩니다. 이는 루프 안에 있으므로 쉽게
    재사용할 수 있도록 루프의 한 반복을 컴파일해야 함을 나타냅니다.

이렇게 하면 기본 eager 모드와 비슷하게 백그라운드 구체화가 시작되지만, 컴파일되는
그래프가 단일 연산보다 크다는 점이 다릅니다. 구체화 신호가 발생했을 때 이미
삭제되었거나 덮어쓴 텐서는 건너뛰며, 일반적으로 다운스트림 연산에 퓨전되거나
출력이 읽히지 않고 버려지면 완전히 제거됩니다. (참고: 분산 집합 통신 연산의
경우 TPU 간 교착 상태를 피하기 위해 데드 코드 제거를 건너뜁니다.)

이 방식은 더 큰 컴파일 그래프를 만들므로, 실행 시간을 개선하기 위해 최적화
수준 2(`-O2`)를 사용합니다. 더 적은 수의 더 큰 그래프를 컴파일하므로 컴파일
스레드 풀의 병렬화 이점이 줄어들어, 컴파일 시간이 strict eager보다 길어질 수
있습니다.

최적화된 eager 모드는 `torch.compile` 모드만큼 최적화되지는 않지만, 모델 코드를
변경하지 않고도 기본 eager 대비 최대 50%의 성능 향상을 보여 줍니다.

## 주의할 점 { #pitfalls }

이 실행 파이프라인은 지연 시간과 처리량 모두에 최적화되어 있지만, 성능이 저하될
수 있는 경우도 있습니다.

### 모든 모드: Python 측 제어 흐름과 데이터 종속 형상 { #all-modes-python-side-control-flow-and-data-dependent-shapes }

PyTorch에서는 의도치 않게, 그리고 알아차리지 못한 채 디바이스-호스트 전송을
강제하기 쉽습니다. "`if my_tensor.all()`"과 같은 연산은 불리언 값
텐서를 암묵적으로 생성하고, 스트림을 동기화하고, 제어 흐름을 계속하기 전에 그
불리언을 CPU로 복사합니다.

기본 eager 모드에서는 이로 인해 새 그래프 중단이 강제되지는 않지만, 진행하기 전에
스트림의 전체 실행 파이프라인을 비워야 합니다. 더 나쁜 점은 최적화된 eager 모드나
컴파일 모드에서 이 강제 동기화 지점이 eager 퓨전 스트림이나 FX 그래프에 그래프
중단을 강제하여 최적화 장벽을 만든다는 것입니다.

`torch.masked_select`와 같이 출력 형상이 데이터에 종속되는 PyTorch 연산에서도
비슷한 동작이 발생할 수 있습니다. 마스크 입력을 평가하기 전까지는 출력 텐서의
크기를 알 수 없으므로, 마찬가지로 진행하기 전에 완전한 블로킹 스트림 동기화와
형상 메타데이터의 디바이스-호스트 전송이 강제됩니다.

### Strict eager 모드: 작은 실행 파일로 인한 마이크로버블 { #strict-eager-mode-tiny-executables-cause-microbubbles }

PjRt에 실행 파일을 대기열에 추가하는 데는 약간의 시간이 걸리며, 일반적으로
50마이크로초 이하입니다. 대부분의 경우 각 실행 파일은 이보다 오래
걸리므로(1~2밀리초라도) 이 지연 시간이 완전히 가려지며, TPU가 최고 효율로
계속 작동하는 정상 상태가 됩니다.

그러나 이 임곗값보다 짧은 실행 파일이 너무 많이 대기열에 추가되면(예: 작은 텐서
크기로 strict eager 모드를 사용하는 경우) TPU 기아 상태가 발생할 수 있습니다.
CPU가 작업을 대기열에 추가하는 속도보다 TPU가 더 빠르게 실행되면, 디스패치
속도가 병목이 되어 TPU 실행이 작지만 잦은 "마이크로버블"로 중단됩니다.

이를 방지하려면 이 작은 실행 시작 오버헤드를 극복할 만큼 모델이 각 연산에서 충분한
양의 작업을 수행하도록 하거나, 최적화된 eager 모드를 사용하여 실행을 즉석에서
컴파일 블록으로 자동 퓨전하세요.

### 컴파일 모드: 인수 또는 출력으로서의 뷰 { #compiled-mode-views-as-arguments-or-outputs }

컴파일된 실행 파일을 호출할 때 PjRt는 입력 값이 연속적이고, 오프셋이 0이며,
특정 데이터 타입일 것을 요구합니다. Tensor 인수가 단순하지 않은 뷰이거나 원래
데이터 타입에서 비트캐스트된 경우, TorchTPU는 컴파일된 실행 파일을 올바르게
호출하기 위해 eager 모드(strict 또는 최적화)에서 텐서의 임시 사본을 만듭니다.

이 임시 사본을 방지하려면 컴파일된 함수의 모든 입력이 연속적인지 확인하세요.
여러 컴파일된 함수를 순서대로 호출하려는 경우, 최적화된 함수 사이에서 eager 모드
마찰이 생기지 않도록 앞선 함수의 출력이 연속적인지 확인하세요.

### 최적화된 eager 모드: 불필요한 텐서 유지 { #optimized-eager-mode-retaining-redundant-tensors }

모든 eager 모드에서 연산은 생성된 순서대로 실행되며, 구체화 신호가 발생할 때마다
그 시점에 살아 있는 모든 Tensor가 구체화됩니다.

이러한 텐서 중 중요하지 않은 중간 텐서가 있으면, defer-and-fuse 메커니즘이
이를 필요한 출력으로 잘못 식별하여 구체화할 수 있으며, 이로 인해 컴파일 그래프의
효율이 떨어질 수 있습니다.

퓨전을 개선하고 메모리 사용량을 최소화하려면 더 이상 필요하지 않은 텐서를
즉시 정리하거나, 인플레이스 연산을 사용하여 오래된 텐서를 현재 값으로
대체하세요.

## 요점 { #takeaways }

TorchTPU의 지연 실행 모델은 다양한 컴파일 시간 / 런타임 절충점에서 효율적인
파이프라이닝을 제공합니다.

*   **컴파일 시간을 최소화하려면:** strict eager 모드(기본값)를 사용하세요. 이
    모드는 즉시 실행을 시작하고 컴파일을 병렬화하여 첫 결과까지의 시간을 최대한
    단축합니다.
*   **워밍업 후 처리량을 최대화하고 지연 시간을 최소화하려면:**
    `torch.compile`을 사용하세요. eager 모드 오버헤드를 거의 모두 제거하고
    컴파일러 최적화 여지를 최대화합니다.
*   **더 빠른 런타임이 바람직하지만 `torch.compile`을 사용할 수 없는 경우:**
    최적화된 eager 모드 사용을 고려하세요.
*   **디버깅하려면:** launch-blocking 모드를 사용하여 CPU와 TPU가 보조를 맞춰
    진행하도록 강제하세요.
*   **강제 동기화를 피하세요:** 연속적인 텐서를 최소한으로 유지하고, 계산
    밀도가 높은 연산을 사용하여 TPU에 생산적인 작업을 충분히 공급하세요.
